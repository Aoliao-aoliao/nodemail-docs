升级与数据迁移 ​

升级目标 ​

升级必须同时保护业务数据、配置和可回退能力。容器可以重建，PostgreSQL 数据、邮件持久化目录、密钥和证书不能随容器删除。

升级前 ​

  1. 阅读更新日志和新增迁移。
  2. 记录当前 Git 提交、镜像和容器状态。
  3. 备份数据库、邮件数据、环境文件和 TLS 配置，并验证备份可读取。
  4. 在隔离环境恢复备份，运行迁移和核心流程。
  5. 安排维护窗口，暂停会造成数据继续变化的入口。

数据库备份示例中的服务名和用户应按实际配置替换：

bash
docker compose exec -T db pg_dump -U <db-user> -Fc <db-name> > database.dump

仅生成文件不等于备份成功。应检查退出码、文件大小，并定期做恢复演练。

执行升级 ​

bash
git fetch --all --prune
git checkout <reviewed-commit>
docker compose build
docker compose up -d
docker compose ps
docker compose logs --tail=300 backend nginx

使用已评审的提交或标签，不要在生产机上直接合并未知分支。后端会运行尚未执行的迁移；当前迁移序列到 048。迁移失败时服务应停止启动，以避免在半迁移状态下继续写入。

验证 ​

  • 健康检查、首页、/app/ 和管理员登录页可访问。
  • 原用户、邮箱和邮件数量与升级前一致，外键和 UID 无异常。
  • 用户及管理员只读接口正常。
  • SMTP、IMAPS、POP3S、Redis、rspamd 和 Nginx 正常。
  • MX、SPF、DKIM、DMARC 与当前配置一致。
  • 静态 Logo、附件和下载响应的状态与内容类型正确。

会产生真实邮件、订单、删除或外部通知的操作，优先在隔离环境验证。生产验证需要使用明确标识的测试账号，并在完成后清理测试数据。

回退 ​

应用代码回退前先判断新迁移是否向后兼容。若不兼容，需要停止写入并从升级前备份整体恢复数据库和对应代码。不要只回退镜像却保留不兼容的新表结构。

回退完成后再次核对数据数量、服务状态和协议端口，并记录失败原因，修复后重新走完整升级流程。
