# 检查与故障排查

## 推荐顺序

1. 用 `docker compose ps` 确认容器状态。
2. 查看出错请求对应服务的近期日志。
3. 在宿主机检查反向代理、端口和证书。
4. 检查数据库、Redis、磁盘和 DNS。
5. 先定位根因，再重启服务；不要用持续重启掩盖错误。

## 页面或 Logo 不显示

确认静态文件已经进入构建产物，Nginx 返回 `200` 和正确的 `Content-Type`。容器中的文件及其父目录必须允许 Web 服务器读取。若曾返回 `403`，修复权限后重建静态镜像，并清理浏览器或 CDN 缓存。

应用位于 `/app/`，检查资源 URL 是否正确带上基础路径。错误的绝对路径常导致首页正常、子页面刷新或图片请求失败。

## 登录失败

- 区分普通用户入口与 `/app/admin/login` 管理员入口。
- 检查账号是否启用、密码是否刚被重置、2FA 时间是否同步。
- OAuth 登录检查提供方开关、客户端配置和回调地址。
- 多次失败后检查限流，不要通过关闭所有安全限制长期绕过。

管理员密码采用哈希保存，无法从数据库读取明文。遗忘后应走受控重置流程并立即设置新密码。

## 邮件客户端无法连接

使用完整邮箱地址和应用专用密码，推荐配置：

```text
IMAP: mail.to9.us:993 SSL/TLS
POP3: mail.to9.us:995 SSL/TLS
SMTP: mail.to9.us:587 STARTTLS
```

分别检查端口连通性、TLS 主机名和有效期、账号状态及应用密码。网页能打开不能证明邮件端口或证书正常。

## 收不到邮件

检查域名 MX 是否指向正确邮件主机、25 端口是否可达、邮箱是否存在且启用、容量是否已满，以及 rspamd 隔离区。再查看后端 SMTP 日志中的接收结果。

## 发信失败

检查邮箱和域名的发信资格、配额、DKIM、SPF、退信状态、抑制名单以及中继服务。临时网络失败等待重试；永久拒绝需要根据远端响应修正。

## TLS 证书没有更新

比较磁盘证书与 587、993、995 实际握手证书的序列号和到期时间。证书续期后，后端必须重新加载；只重载网页 Nginx 不会自动更新邮件协议证书。

同时确认自动续期任务保存了正确的安装路径和重载命令，并限制私钥文件权限。

## 迁移失败

保留第一条迁移错误及其前后日志，确认数据库版本和已执行迁移记录。不要删除迁移记录或强行跳过。先在备份副本复现并修复，再恢复生产升级。

## 订单未到账

按订单号检查支付平台交易、服务端回调签名、回调响应、订单状态和钱包流水。使用幂等补偿，禁止重复手工加款。

## 提交工单需要的信息

提供发生时间、账号或邮箱、页面路径、操作步骤、订单号或邮件 ID，以及去除敏感信息后的错误文本。不要提交密码、API 密钥、Cookie、验证码、支付密钥或 TLS 私钥。
